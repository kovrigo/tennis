# Разработка первой версии: сайт Федерации тенниса ЛО

Бриф, объём и дизайн одобрены. Здесь — как устроить сайт для разработчика: хранение, обновления базы, образцы, вход и права, файлы, счёт судьи, обновление онлайн-счёта, ответы API, проверка состояния, запуск и тесты. Кода ещё нет.

## Итог

- Решений руководителя не требуется. Бриф не менялся.
- Новых зависимостей нет. Хватает Node 22 (`node:sqlite`, `node:crypto`) и того, что уже в проекте: React, Vite, Vitest, tsx.
- Один процесс сервера, один файл базы. База и файлы положений лежат в папке `data/` рядом с кодом. Внешняя база не нужна.
- Каждое решение — самое простое, которое проходит приёмку. Что нужно только к публичному запуску — в конце.

## Что уже есть

- `server/index.ts`: HTTP-сервер Node на `127.0.0.1`. В разработке страницы отдаёт Vite с горячей перезагрузкой, в рабочем режиме — собранная папка `dist/`. Неизвестный путь получает `index.html`.
- `server/api.ts`: `/api/health` отвечает `ok` и `commit`.
- `server/api.test.ts`: тест поднимает обработчик на порту 0. Этот приём сохраняется.
- Разработка: `paneweb up` запускает `bun run dev` из `.paneweb.json`.
- Тестовый сайт:
  - запускает `.staging-site.json` из основной копии репозитория на ветке `staging`: установка, сборка, старт;
  - забирает новый `staging` с GitHub примерно раз в 5 минут, останавливает старый процесс со всеми дочерними и запускает новый;
  - передаёт сайту только `PORT`;
  - ничего не чистит: файлы, которые git игнорирует, переживают обновление.

## Хранение данных

- База — SQLite через встроенный `node:sqlite` (`DatabaseSync`). Файл `data/tennis.sqlite`.
- В `.gitignore` добавляется `/data/`, только корневая папка.
  - На тестовом сайте это `data/` основной копии. Обновление кода её не трогает.
  - У каждой рабочей копии своя `data/`. Задачи не делят данные. Локальные данные не попадают на тестовый сайт.
- Сервер при старте создаёт `data/`, `data/files/` и `data/backups/`, если их нет.
- При открытии базы: `journal_mode=WAL`, `foreign_keys=ON`, `busy_timeout=5000`.
- Сервер — один процесс. `DatabaseSync` синхронный, поэтому два запроса не перемешивают свои записи.
- Транзакции — одна функция `tx(db, fn)`:
  - внешний вызов — `BEGIN IMMEDIATE … COMMIT`, вложенный — `SAVEPOINT`. Так образцы вызывают функции сохранения со своими транзакциями;
  - при ошибке откат;
  - `fn` синхронная. Если она вернула промис, `tx` бросает ошибку.
- Все запросы идут через обёртку в `server/db.ts`. Она превращает `undefined` в `NULL`, а `true` и `false` — в 1 и 0. Без неё `node:sqlite` бросает ошибку на необязательном поле.
- Сортировка и сравнение русских имён — в коде, через `Intl.Collator("ru", { numeric: true })`. SQLite не знает строчных кириллических букв. Так же сортируются корты: «Корт 2» раньше «Корт 10».
- Предупреждение Node `ExperimentalWarning: SQLite is an experimental feature` отключается флагом `--disable-warning=ExperimentalWarning` в `NODE_OPTIONS` скриптов `dev`, `start`, `test`.
- Версия Node на сервере зафиксирована. Смена API `node:sqlite` затронет только `server/db.ts`.
- Время:
  - дни турниров и матчей хранятся как `YYYY-MM-DD`, время матча — `HH:MM`, по Москве;
  - моменты (действия судьи, сессии) — строки ISO в UTC;
  - «сегодня» считает сервер в `Europe/Moscow` через `Intl.DateTimeFormat`. Часам телефона не доверяем;
  - сервер отдаёт готовые московские дату и время для показа, например «14:32». Страница часовые пояса не пересчитывает.

### Что хранится

- `users`: организатор и судьи. Роль, имя, фамилия, логин (уникальный, строчными латинскими), хеш пароля.
- `sessions`: хеш токена, пользователь, срок.
- `contacts`: одна строка — адрес, телефон, почта.
- `rating_groups`: название, порядок.
- `files`: случайный идентификатор, исходное имя, тип, размер.
- `tournaments`: название, даты, город, место, тип (`rtt` или `amateur`), категория, файл положения.
- `divisions` — разряды: турнир, название, рейтинговая группа. Группа обязательна, только если есть таблица очков.
- `points_rows`: строки таблицы очков — разряд, название места, очки, порядок.
- `placements`: места игроков — разряд, игрок, строка таблицы или место текстом. Место ссылается на строку по её номеру, поэтому переименование строки места не сбрасывает (S7.9).
- `players`: имя, фамилия, город.
- `matches`: разряд, круг, день, время, корт, игроки на сторонах `a` и `b`, судья. Итог вручную: сторона победителя, сеты, пометка. Состояние (`not_started`, `running`, `finished`), начало и конец.
- `score_actions`: журнал действий судьи — матч, номер по порядку `seq`, очко или отмена, сторона, `requestId`, судья, время. Строки только добавляются.
- `create_requests`: `requestId` уже выполненных созданий записей у организатора. Защищают от двойного создания.
- `news`: заголовок, дата, текст.
- `schema_migrations`, `seed_runs`: что уже применено.

Счёт, геймы, сеты и судьи протокола не хранятся. Их считает одна чистая функция `scoreFromActions(actions)` в `server/score.ts`: очко кладёт на стек, отмена снимает последнее. Состояние, начало и конец в `matches` пишет только функция действия судьи и формы итога вручную, в той же транзакции. По ним быстро находятся идущие матчи.

### Удаление и связи

- Удалить можно: новость; матч без засчитанных очков; игрока без матчей; турнир без матчей, вместе с его разрядами, таблицами и файлом.
- Разряды, судьи, группы и контакты не удаляются. В дизайне удаления для них нет.
- Внешние ключи без `ON DELETE CASCADE`, кроме удаления турнира и матча. Ошибка в коде не сотрёт очки или места.
- Игрок больше не играет в разряде (матч удалён или игрок заменён) — его место в этом разряде снимается в той же транзакции. Иначе невидимое место считалось бы в рейтинге.
- У разряда впервые появилась таблица очков — места текстом снимаются при этом же сохранении. Места затем отмечаются из строк таблицы.

## Обновления базы

- Файлы `server/migrations/NNN_name.sql`. Первый — `001_init.sql`, вся схема.
- Сервер применяет новые файлы при старте, до того как начнёт принимать запросы. Применяется каждый файл, которого нет в `schema_migrations`, по порядку имён.
- Порядок для каждого файла:
  1. `PRAGMA foreign_keys = OFF`.
  2. `BEGIN IMMEDIATE`. Проверка, что файл ещё не применён, — внутри транзакции.
  3. Сам файл.
  4. `PRAGMA foreign_key_check`. Нарушение — откат и ошибка.
  5. Строка в `schema_migrations`: имя, контрольная сумма sha256, время. `COMMIT`.
  6. `PRAGMA foreign_keys = ON`.
- Так пересборка таблицы по правилам SQLite не стирает связанные строки.
- Перед первым новым файлом сервер копирует непустую базу:
  - `VACUUM INTO 'data/backups/before-NNN_name-<время UTC>.sqlite.tmp'`, затем переименование без `.tmp`;
  - оставшиеся `.tmp` от прерванного старта удаляются;
  - копия не удалась — обновления не применяются, проверка состояния показывает ошибку.
- Применённый файл изменился или пропал — сервер пишет это в журнал и в проверку состояния (`drift`), но новые файлы применяет. Иначе одна правка пробела навсегда остановила бы выпуски.
- Файл не применился — сервер всё равно стартует:
  - `/api/health` отвечает 503 с именем файла и текстом ошибки;
  - остальные `/api/*` отвечают 503 `not_ready`;
  - страницы показывают обычное «Не удалось загрузить страницу» из дизайна.
- Правила:
  - Применённый на тестовом сайте файл не меняют никогда. Нужна правка — новый файл.
  - Лучше добавлять таблицы и столбцы. Переименование или удаление столбца — пересборкой таблицы в том же файле.
  - До слияния в `staging` свой последний файл можно править. Локально после этого — чистая база.

## Образцы

- Файлы `server/seeds/NNN_name.ts`. Каждый экспортирует `run(db, ctx)`. Список — явный, в `server/seeds/index.ts`.
- Запускаются при каждом старте, после обновлений базы.
- Каждый файл выполняется один раз на базу. Проверка `seed_runs`, сами образцы и запись имени — в одной транзакции. Поэтому:
  - повторный выпуск образцы не дублирует;
  - удалённый или изменённый организатором образец не возвращается;
  - даты образцов отсчитываются от первого запуска и дальше не сдвигаются.
- Файл образцов упал — его транзакция откатывается, сервер пишет ошибку в журнал и работает дальше. Проверка состояния отвечает 503 с ошибкой, поэтому выпуск её заметит.
- Новые образцы позже — новый файл. Правила для него:
  - прежние образцы ищет по названию или логину, а не по номеру. Не нашёл — пропускает;
  - не создаёт логин или запись, которая уже может быть у организатора.
- Правка уже выполненного файла на тестовый сайт не попадёт. Локально после правки — чистая база.
- Образцы сохраняются теми же функциями, что и формы организатора. Очки — той же функцией, что и действия судьи, с переданным временем: 30–90 секунд между очками. Так в образцах нет невозможного счёта, а у протокола правдоподобные начало и конец.
- `001_samples.ts` создаёт то, что требует объём:
  - три турнира от московской даты первого запуска: идущий (вчера — завтра), предстоящий (через 14–16 дней), завершённый (21–19 дней назад). Один из них — РТТ без таблицы очков;
  - две рейтинговые группы и 16 игроков;
  - в завершённом турнире — 7 матчей с итогами, один из них в три сета с тай-брейками, места и очки;
  - в идущем — матчи на сегодня: один идёт с очками, один завершён, один с итогом вручную, остальные не начаты;
  - три новости и контакты-образцы;
  - учётные записи: `organizer` с паролем `tennis-org`, `judge1` с паролем `tennis-judge1`, `judge2` с паролем `tennis-judge2`. Судьи назначены на сегодняшние матчи;
  - положения: один файл в репозитории, `server/seeds/files/sample-regulation.pdf`, с надписью «Образец положения. Не документ федерации». Каждому турниру — своя копия в `data/files/`.
- На тестовом сайте образцы остаются такими, какими появились. Начатый образец-матч там может закончить кто угодно. Проверки, которым нужны свежие образцы, идут на своём сайте разработки с чистой базой.

## Вход и права

- Роли: `organizer` и `judge`. Организатор заводится только образцами. Судей заводит организатор.
- Пароль: асинхронный `scrypt` из `node:crypto` со случайной солью, сравнение через `timingSafeEqual`. Не короче 8 знаков.
- Неизвестный логин тоже проходит хеширование, с подставным хешем. По времени ответа нельзя узнать, есть ли логин.
- Сессия:
  - случайный токен 32 байта в cookie `HttpOnly; SameSite=Lax; Path=/; Max-Age=86400`;
  - имя cookie — `tennis_session_<PORT>`. Тестовый сайт и сайты разработки разных задач живут на одном адресе с разными портами, а cookie порты не различают. С общим именем вход на одном сайте выбивал бы вход на другом;
  - в базе — только sha256 токена;
  - срок — 24 часа после последнего запроса. Сервер продлевает его и заново отправляет cookie не чаще раза в час. Этого хватает на весь игровой день, даже если закрыть браузер (S9.12);
  - выход удаляет сессию. Новый пароль судьи удаляет все его сессии.
- Ограничение входа (S6.9):
  - после 5 неверных паролей подряд логин закрыт на 15 минут, в том числе несуществующий;
  - ответ 429 содержит число минут для сообщения «Слишком много попыток. Попробуйте через N мин.»;
  - верный пароль сбрасывает счётчик;
  - счётчик в памяти. Просроченные записи удаляются при каждой неудаче. Перезапуск сервера счётчик обнуляет.
- Права:
  - маршруты — таблица `[метод, шаблон, роль, обработчик]`, роль — `public`, `organizer` или `judge`;
  - пути `/api/admin/*` — только `organizer`, `/api/judge/*` — только `judge`;
  - действие в матче — только если матч назначен этому судье и итога вручную нет;
  - публичные маршруты — только чтение, кроме входа и выхода;
  - без сессии — 401 `unauthorized`, чужая роль — 403 `forbidden`.
- Защита от запросов с чужих сайтов:
  - запись принимает только тело `application/json`. Исключение — загрузка файла методом `PUT`;
  - такие запросы браузер с чужого адреса без разрешения не отправит, а сервер разрешений не даёт;
  - `SameSite=Lax` здесь не защищает: сайты на соседних портах того же адреса браузер считает своими.
- Страницы прячут то, что роли недоступно. Решает всё равно сервер.

## Файлы положений

- Загрузка: `PUT /api/admin/tournaments/:id/regulation?name=<имя файла>`. Тело — сам файл, без разбора multipart. В браузере: `fetch(url, { method: "PUT", body: file })`.
- Сервер:
  - `Content-Length` больше 20 МБ — сразу 413 `too_large`, тело не читается, соединение закрывается;
  - без `Content-Length` перестаёт читать после 20 МБ с тем же ответом;
  - проверяет расширение (`.pdf`, `.doc`, `.docx`) и первые байты (`%PDF`, `PK`, `D0 CF 11 E0`). Иначе 400 `bad_file_type`;
  - тип для скачивания берёт по расширению, а не из запроса;
  - имя обрезает до 200 знаков и убирает управляющие символы и кавычки;
  - пишет файл в `data/files/<случайный идентификатор>`, затем в одной транзакции сохраняет строку `files` и ссылку у турнира;
  - при ошибке базы удаляет новый файл. Старый файл удаляет только после сохранения.
- Скачивание: `GET /api/files/:id`.
  - Заголовки: сохранённый тип, `X-Content-Type-Options: nosniff` и `Content-Disposition: attachment` с двумя именами: латинским `filename="regulation.pdf"` и полным `filename*=UTF-8''…`.
  - Строка есть, а файла на диске нет — 404.
  - Имя и размер для кнопки страница берёт из `files`.
- Удаление: `DELETE /api/admin/tournaments/:id/regulation`. Пока у разрядов есть таблицы очков — отказ 409 `in_use`.
- Форма турнира:
  - страница сама проверяет размер и расширение до отправки;
  - сначала сохраняет поля, затем отправляет файл с номером турнира;
  - если файл не принят, турнир уже сохранён, а у поля файла — сообщение из дизайна.
- Файлы лежат в `data/files/` и переживают выпуски так же, как база.

## Счёт судьи

Запрос: `POST /api/judge/matches/:id/actions` с телом `{ requestId, type, side, expectedSeq }`.

- `requestId` — `crypto.randomUUID()`, новый на каждое нажатие. «Отправить снова» шлёт тот же.
- `type` — `point` или `undo`. `side` — `a` или `b`, только для очка.
- `expectedSeq` — номер последнего действия в счёте, который видит судья. До первого очка — 0.

Сервер делает всё в одной транзакции, строго в таком порядке:

1. Матч назначен этому судье, иначе 403 `not_your_match`. Итога вручную нет, иначе 409 `manual_result`.
2. Такой `requestId` у этого матча уже есть:
   - тот же тип и сторона — ничего не меняет и отвечает 200 с текущим счётом. Это повтор после потерянного ответа;
   - другой тип или сторона — 400 `validation`.
3. `expectedSeq` не равен номеру последнего действия — 409 `stale` с текущим счётом (S9.11).
4. Очко после конца матча — 409 `finished`. Отмена без очков — 409 `nothing_to_undo`.
5. Отмена после конца матча, если московская дата последнего очка раньше сегодняшней, — 409 `undo_closed`. Сообщение — «Исправить итог может организатор» из дизайна.
6. Новая строка журнала с номером на 1 больше. Обновление состояния, начала и конца матча. Ответ 200 с новым счётом.

- Шаг 2 идёт раньше шага 3. Иначе повтор уже сохранённого очка был бы отклонён как устаревший.
- Номер растёт и при отмене. Поэтому «отмена, затем очко другому игроку» тоже меняет номер, и нажатие по старому счёту не пройдёт.
- `requestId` проверяется как UUID.
- Ответ 200 и 409 `stale`: `{ score, seq }`. `score` — сеты, текущий гейм, тай-брейк, конец матча, победитель.
- Страница:
  - блокирует кнопки сразу при нажатии, до перерисовки. Двойное касание не отправит два действия;
  - пока действие не сохранено, ничего больше не шлёт (дизайн);
  - ждёт ответа 10 секунд через `AbortController`.
- Новый судья после замены продолжает с текущего номера. Организатор снял итог вручную — судья снова ведёт матч с сохранённых очков.
- Правила счёта — в `scoreFromActions`: до двух выигранных сетов, сет до 6 с разницей в два, при 6:6 тай-брейк до 7 с разницей в два в каждом сете, гейм с «больше-меньше».
- Отмена — тот же пересчёт без последнего очка. Отмена через границу гейма, сета и тай-брейка не требует отдельного кода.
- Протокол собирает сервер: 7:6(5), ход по геймам, начало и конец по первому и последнему засчитанному очку, все судьи засчитанных очков. Табло на странице показывает только счёт с сайта.
- Начатый и брошенный матч остаётся «идёт», как требует объём. Закрывает его организатор итогом вручную.

## Обновление онлайн-счёта

- Страница спрашивает `GET /api/live` каждые 10 секунд, считая от начала прошлого запроса. Ожидание — 8 секунд. «Нет связи» — когда удачному ответу больше 30 секунд. Всё по дизайну.
- В скрытой вкладке опрос стоит. При возвращении — сразу новый запрос.
- Ответ: три группы из дизайна — идут сейчас, ещё не начались, завершены сегодня. Плюс московское время ответа для «обновлено в 14:32».
- Блок «Сейчас на кортах» на главной берёт тот же ответ.
- WebSocket и поток событий не нужны:
  - опрос раз в 10 секунд укладывается в 15 секунд с запасом;
  - не держит соединений и проходит через прокси тестового сайта без настройки;
  - десяток зрителей — это один запрос в секунду. Пересчитываются только сегодняшние и идущие матчи.
- Экран судьи не опрашивает. Счёт приходит в ответе на каждое действие. При возвращении на вкладку экран перечитывает `GET /api/judge/matches/:id`.

## API

- Всё под `/api/`, JSON в UTF-8. Каждой публичной странице — один запрос, поэтому у страницы одно состояние загрузки.
- Публичные, `GET`, без входа:
  - `/api/health`;
  - `/api/site` — контакты для подвала и вошедший сотрудник для ссылки в шапке. Запрашивается один раз при открытии сайта;
  - `/api/home`, `/api/tournaments`, `/api/tournaments/:id`, `/api/live`;
  - `/api/matches/:id` — протокол;
  - `/api/rating?group=:id`, `/api/players/:id`, `/api/news`, `/api/news/:id`;
  - `/api/files/:id`.
- Вход: `POST /api/login`, `POST /api/logout`.
- Судья: `GET /api/judge/matches`, `GET /api/judge/matches/:id`, `POST /api/judge/matches/:id/actions`.
- Организатор, `/api/admin/…`:
  - турниры, разряды, матчи, игроки, судьи, новости, группы: `GET` список, `GET /:id`, `POST` создать, `PUT /:id` сохранить;
  - `DELETE /:id` — только у турниров, матчей, игроков и новостей;
  - контакты: `GET` и `PUT /api/admin/contacts`;
  - таблица очков сохраняется вместе с разрядом. Строки — `[{ id, name, points }]`, порядок — по списку. Строка с `id` обновляется, без `id` создаётся, пропавшая удаляется. Пропавшая строка с отмеченными местами — 409 `in_use` с числом игроков;
  - таблица очков без положения у турнира — 400 `validation` (S7.3);
  - места — целым списком: `PUT /api/admin/divisions/:id/placements`;
  - итог вручную: `PUT` и `DELETE /api/admin/matches/:id/result`. Обычное сохранение матча итог не трогает;
  - положение: `PUT` и `DELETE /api/admin/tournaments/:id/regulation`.
- Создание (`POST`) несёт `requestId`, созданный при открытии формы. Повтор с тем же `requestId` возвращает уже созданную запись. Так «Сохранить ещё раз» после потерянного ответа не создаст двойника.
- Ответ при успехе — сам объект. Запись возвращает сохранённый объект.
- Ответ при ошибке — код HTTP и `{ error, message, fields }`:
  - `error` — код из закрытого списка. По нему страница выбирает поведение, например жёлтую плашку при `stale`;
  - `message` и `fields` — русские тексты из дизайна. Страница показывает их как есть;
  - тексты для случая «сайт не ответил» — у самой страницы.
- Коды:
  - 400: `validation`, `bad_file_type`, `bad_request` (неверный адрес или тело);
  - 401: `bad_credentials` (неверный логин или пароль), `unauthorized` (нет входа или вход истёк);
  - 403: `forbidden`, `not_your_match`;
  - 404: `not_found`;
  - 409: `stale`, `finished`, `nothing_to_undo`, `undo_closed`, `manual_result`, `in_use`, `duplicate`, `login_taken`;
  - 413: `too_large`;
  - 429: `too_many_attempts`;
  - 500: `server`;
  - 503: `not_ready`.
- Повтор игрока (S6.3): `POST /api/admin/players` отвечает 409 `duplicate` со списком совпадений. Форма показывает предупреждение и отправляет снова с `confirmDuplicate: true`. Совпадение ищется без учёта регистра, «ё» равна «е».
- Удаление: списки и формы получают число матчей и очков. По ним страница прячет кнопку и пишет причину. Сервер всё равно отказывает с 409 `in_use`.
- Организатор правит без проверки версий: сохраняется последнее. Роль одна, сайт тестовый.
- Тело JSON — не больше 1 МБ, иначе 413.
- Заголовки: `Cache-Control: no-store` у всех `/api/*`, кроме файлов. `X-Content-Type-Options: nosniff` и `X-Frame-Options: DENY` у всех ответов.
- Типы запросов и ответов — в одном файле `src/api-types.ts`. Его импортируют и сервер, и страницы. Без генерации кода и без библиотек схем.
- Проверка полей — на сервере, вручную, по сущностям, с русскими текстами.
- `handleApi` становится асинхронным и возвращает `Promise<boolean>`. `server/index.ts` ждёт его ответа и только потом отдаёт запрос Vite или файлам.
- На страницах — свой маленький маршрутизатор на `history.pushState`, без библиотеки.
- Отсутствующий файл под `/assets/` получает 404, а не `index.html`. Вкладка со старой версией после выпуска покажет «Не удалось загрузить страницу» с кнопкой «Обновить».

## Проверка состояния

`GET /api/health`:

- Норма — 200: `{ "ok": true, "commit": "<sha>", "migration": { "latest": "001_init", "pending": 0 }, "seed": { "latest": "001_samples", "pending": 0 } }`.
- Применённый файл обновления изменён или пропал — то же, с `"drift": ["001_init"]` внутри `migration`.
- Сбой при старте — 503, `"ok": false` и `"error": "<шаг>: <текст>"`. Шаг — `db`, `backup`, `migration` или `seed`.
  - При сбое `db`, `backup` или `migration` остальные `/api/*` отвечают 503 `not_ready`.
  - При сбое `seed` сайт работает, но выпуск увидит 503.
- Выпуск открывает этот адрес и ждёт свой коммит, свой последний файл обновления и `pending` 0.
- Текст ошибки SQLite виден всем, кто откроет адрес. Для тестового сайта это допустимо.

## Сбои и журнал

- Весь обработчик запроса, включая отдачу файлов, — в одном `try/catch`.
  - Неверный адрес (`decodeURIComponent` бросает ошибку) — 400 `bad_request`.
  - Остальное — 500 `{ "error": "server", "message": "Ошибка на сайте. Попробуйте ещё раз." }`. Внутренности ошибки пользователь не видит.
- Необработанные `unhandledRejection` и `uncaughtException` пишутся в журнал. Процесс не падает от ошибки одного запроса.
- По `SIGTERM` сервер закрывает базу и выходит.
- Сервер пишет в stdout:
  - строку старта: порт, Node, коммит;
  - каждый применённый файл обновления и образцов;
  - каждую ошибку 500 с методом, путём и стеком.
- На тестовом сайте stdout попадает в журнал сайта.

## Шрифты

- Onest и Oswald (woff2, латиница и кириллица) лежат в репозитории, в `src/fonts/`. Лицензия SIL OFL это разрешает.
- Браузер посетителя обращается только к сайту, не к Google Fonts.

## Запуск у разработчика

В README появляется раздел «Начать»:

1. `bun install`.
2. `paneweb up`. Первый старт создаёт `data/tennis.sqlite` с образцами.
3. Войти образцом: `organizer` / `tennis-org`, `judge1` / `tennis-judge1`, `judge2` / `tennis-judge2`.

- Проверка за две минуты: окно шириной с телефон, вход `judge1`, отметить очко. На онлайн-счёте в другой вкладке оно появится в течение 10 секунд.
- Чистая база: `paneweb down`, `rm -rf data/`, `paneweb up`. Нужна:
  - после правки своего ещё не слитого файла обновления или образцов;
  - когда локальные образцы устарели: их даты отсчитаны от дня первого запуска, и сегодняшних матчей уже нет.
- Сервер вручную (`bun run dev`) не запускают.
- `bun run dev` следит и за `server/migrations/*.sql` (`tsx watch --include`). Новый файл обновления применяется сразу.
- Vite не следит за `data/` и `tmp/` (`server.watch.ignored`). Запись в базу не будит сборщик.

## Что отложено до публичного запуска

Объём уже требует к запуску убрать образцы, завести настоящих сотрудников, политику данных и резервные копии. Для разработки к этому добавляется:

- настоящие учётные записи организаторов и смена их пароля — до удаления образцов, иначе не останется ни одного организатора;
- резервные копии `data/` целиком, вместе с файлами, по расписанию;
- флаг `Secure` у cookie и свой домен;
- удаление образцов — новым файлом обновления, а не вручную;
- ограничение входа по адресу, а не только по логину. Сейчас пять неверных попыток закрывают вход судье на 15 минут. Сайт доступен только своим, поэтому это допустимо;
- счётчик неверных входов в базе, если серверов станет больше одного.

## Риски

- Тестовый сайт останавливается на время сборки при каждом выпуске, примерно на минуту. Судья в это время видит «Не сохранено: сайт не ответил» и отправляет снова. Очко не теряется и не задваивается.
- `node:sqlite` в Node 22 экспериментальный. Обновление Node может поменять его API. Правка — в одном файле `server/db.ts`.
- Данные тестового сайта лежат в основной копии репозитория. Если её пересоздадут, образцы появятся заново, а правки организатора пропадут. Копии базы делаются только перед обновлением базы, в той же папке.
